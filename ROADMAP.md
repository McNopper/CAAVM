# Hephaestus ROADMAP — the agentic harness

**Vision.** One repository. Intelligence lives in `.opencode/` (agents, skills) and MCP servers; the Eclipse plugin (`eclipse/`) is the harness: it hosts, services, and observes headless agents working in isolated git worktrees. The human uses Eclipse as PM + reviewer; agents self-organize via the task board. **Prime rule: never build in the plugin what Hephaestus already provides — and what it provides moves into the Maven/Eclipse world when we touch it.** Epics, sprints and milestones become **purely Maven-reflected** over the version-controlled task store.

## H5 — opencode deep integration (adopted 2026-08-23; uses the verified v1.18.21 surface — every endpoint below exists in the current spec)
*Research verdict context: our differentiators are the process layer (Scrum/V-model + paired verification) and the cost loop; the field's table stakes we still lack are permissions plumbing, PR/CI closure, sandboxing, remote access. H5 closes everything reachable through the opencode API itself.*
1. **Permission requests — unattended-fleet gating** (research rec #1): client `GET`-driven permission queue via SSE permission events + `POST /session/:id/permissions/:permissionID` `{response, remember}`; Board/Fleet badge "needs input" with peek→approve/deny; remembered rules land in the worktree session config. *Unblocks trustworthy unattended sprints.*
2. **Per-job diffs via `GET /session/:id/diff`**: Fleet view *Open diff* switches from local `git HEAD..opencode/<id>` to the server's authoritative per-session `FileDiff[]` (works for taken-over/external sessions too); diff viewer lists files + per-file patch.
3. **Official take-over via `/tui/*`**: replace the "open a chat window on the same session" approximation with the real IDE mechanism — `POST /tui/append-prompt`, `/tui/submit-prompt`, `/tui/open-models`, `/tui/show-toast`; *Take over* routes through the TUI control channel when present, chat-resume stays fallback.
4. **Repo map & semantic find**: client `GET /find` (text), `/find/file`, `/find/symbol`, `/file`, `/file/content`, `/file/status` → an Eclipse *Repo view* (file tree + fuzzy file/symbol search) + a `repo-map` skill for agents (context gathering without shell greps); `/file/status` feeds a *Working set* node in the Server view.
5. **Slash-command execution** `POST /session/:id/command` + shell `/:id/shell`: chat view gets the project's custom commands (from `.opencode/command/`) in the composer; Fleet jobs may run a command as bootstrap step.
6. **Session lifecycle tools** — `/:id/fork` (explore-a-variant from Session details), `/:id/revert`/`/unrevert` (message rollback — partial checkpoint story), `/:id/summarize` (compact long fleet sessions before mergeBack), `/:id/share`/`DELETE share` (read-only share link on the ticket as a `url` artifact; opt-in, off by default).
7. **Project/VCS awareness**: `GET /project`, `/project/current`, `/vcs`, `/path` → Server view header + `ProjectContext` cross-check (spawn-cwd sanity), Board shows branch/dirty state next to the store root.
8. **Live config `PATCH /config` + provider auth `GET /provider/auth` + `POST /provider/:id/oauth/*`**: Providers view gains connect/auth-state per provider (OAuth flow via external browser + callback port), model switch without editing files.
9. **Global event stream `GET /global/event`**: multi-connection fleet observability (today each connection filters its own `/event`; a global subscription per connection de-duplicates cross-server events for the Fleet view).

- **Board = multi-level structure** (design principle, confirmed): the Pipeline layout's V-model stages ARE the abstraction levels (requirements → architecture → design → implementation), each with a dedicated paired verification stage — that pairing is why the output stays reliable and the process stays structured *at hundreds of agents*. Future polish candidate: level-based collapse/rollup (epic → level → tickets) once fleet sizes demand it.
- **Distributed fleets — several opencode servers on different machines, one common board** (design principle, confirmed): the store is plain git-versioned Markdown, so N machines share one board by sharing the repo; each machine's Eclipse serves its own `eclipse-build` endpoint + worktree sessions; the store is the ONLY shared state. Claim semantics across machines = git discipline (pull → claim → push; a push conflict means re-claim). Follow-ups when it goes live: surface the store's git state (branch/ahead/behind) in the Board header, a sync helper around `plan_sprint`/`close_sprint`, and a doc page on sharding vs single-repo.
