# Hephaestus ROADMAP — the agentic harness

**Vision.** One repository. Intelligence lives in `.opencode/` (agents, skills) and MCP servers; the Eclipse plugin (`eclipse/`) is the harness: it hosts, services, and observes headless agents working in isolated git worktrees. The human uses Eclipse as PM + reviewer; agents self-organize via the task board. **Prime rule: never build in the plugin what Hephaestus already provides — and what it provides moves into the Maven/Eclipse world when we touch it.** Epics, sprints and milestones become **purely Maven-reflected** over the version-controlled task store.

## H6 — Dataflow V-pipeline (user direction, adopted 2026-08-23 — the future execution model)
**Expectation: every V-model stage executes as soon as — and only when — it is not dependent on unfinished upstream work and no new/changed information is pending for it.** Concretely: a dispatcher (PM agent or harness-side scheduler over the store) continuously computes the *runnable set* from the board — a stage runs when its upstream definition stage is done AND its inputs have not changed since its last run (change = the defining ticket's `updated_at` moved / a send-back occurred); a changed upstream invalidates downstream artifacts (re-run or explicit re-confirm). This turns the V-model from "stages available in parallel" into a **self-draining dataflow graph**: no stage ever waits for a human to notice it became runnable, and nothing re-runs needlessly. Building blocks that already exist: the stage field + `task_advance`/`task_send_back` semantics, sprints, atomic claims, FleetRunner's per-ticket launch, SSE-driven completion. Missing pieces (candidates, in order): (1) ~~dependency+staleness rule as a small SWT-free/agent-agnostic function over the store~~ ✅ **`StageReadiness` landed (wave 3, tasks bundle, exported)** — `evaluate(List<Task>) → Map<ticketId, Readiness{Kind, reason}>`, pure (no I/O/clocks/OSGi); Kind ∈ READY / WAIT_UPSTREAM / STALE / BLOCKED / RUNNING / NOT_APPLICABLE with precedence NOT_APPLICABLE→RUNNING→BLOCKED→WAIT_UPSTREAM→STALE→READY, done+fresh→NOT_APPLICABLE. Store-reality rules: upstream evidence = own gated advance history (`"advanced to <stage>"`) OR epic-chain sibling/parent at the upstream stage done/in-review; send-backs land as blocked-flag → BLOCKED, after clearBlocked the ticket is READY for rework; STALE = upstream updatedAt strictly AFTER downstream's. 24 tests. (2) ✅ **Auto-dispatch policy landed (wave 4, board)** — `AutoDispatch` SWT-free record `(maxConcurrent, costBudgetUsd, includeStale)` + pure `plan(tasks, readiness, cost, alreadyRunning) → DispatchPlan(launch, skipped[why])`: STALE-before-READY deterministic ordering, running-jobs counted against the cap, cost gate on CostOverview's project grand total with `ESTIMATED_COST_USD = 0.05` per launch (calibrate via the cost loop later), budget 0 = unlimited; Board toolbar *Auto-dispatch* action (fixed policy `of(4, 0, true)` this wave — config deferred) launches the plan sequentially and reports `Launched n, skipped m`; 18 tests. (3) ✅ **Invalidation records landed (wave 4, tasks)** — `TaskStore.recordInvalidations(project)`: for every STALE ticket appends history `inputs changed: upstream <id> updated <iso-ts>` by `h6` under the store's exact locking/write discipline, idempotent (same upstream+ts not re-marked; changed-again yields a second marker); `StageReadiness.staleCause` exposes the blamed upstream; note: the `updatedAt` touch can cascade one STALE level per run — converges (documented); 9 tests. Plus **`task_readiness` MCP tool** (21st in the pack; `{project}` → `{id, stage, kind, reason}` rows ordered STALE→BLOCKED→WAIT_UPSTREAM→RUNNING→READY→NOT_APPLICABLE) so the PM agent can ask "what's runnable"; 9 tests. (4) ✅ **Scheduler + guardrails landed (wave 5, board)** — `DispatchScheduler` SWT-free (policy + sprint-scoped `Supplier<List<Task>>` — the scheduler never sees out-of-sprint tasks — + cost/running suppliers + launch consumer + injectable Clock and executor; `tick()` never throws, best-effort launch failures don't kill the loop; 2-min launch-echo hold guards against lagging running-sets): Board toolbar *Auto ▶/■* toggle runs it at a 30 s period over the current sprint, re-reading suppliers per tick (new tickets drain automatically), stop on uncheck/dispose; wave-4 manual action stays. 14 tests. (5) ✅ **H6 polish landed (wave 6, board)** — `DispatchPolicyStore` (SWT-free, injectable backend; Eclipse instance-scope node `com.opencode.ide.board.dispatchPolicy`, keys maxConcurrent/costBudgetUsd/includeStale/bootstrapAgent/bootstrapCommand; clamping + corrupt→defaults documented; 10 tests) + *Dispatch settings…* toolbar dialog; manual + Auto actions plan with the stored policy; `AutoDispatch` gained `estimateUsd` component + `calibratedEstimate(CostOverview)` (mean per-ticket actual, <3 samples → fallback 0.05, 4-decimal rounding; 11 tests); stored `Bootstrap` rides every launch via a `Supplier<Bootstrap>` seam on `TaskFleetLauncher` (3 tests). **H6 is functionally complete** — the estimate keeps self-calibrating as `fleet actuals:` accrue.
